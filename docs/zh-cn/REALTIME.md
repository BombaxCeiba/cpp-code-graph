# cpp-code-graph — 实时更新（`ccg update` + 编辑器钩子）

本文讲解一次性（one-shot）实时刷新机制：`ccg update` 命令的语义、以数据库为协调中心的队列/认领协议，以及如何为编辑器或代理接线（以 Claude Code 为实例演示），使索引跟踪每一次保存——**全程没有任何守护进程在运行**，也**不在任何地方放置锁文件**。

命令参考：`CLI.md` 的 *ccg update* 一节。

## 1. 为什么采用一次性模式、为什么由数据库担任协调者

每次刷新都是一个短生命周期的进程，只做有限的工作量（通常一到两个 TU）。守护进程会引入第二套需要调试的生命周期、一套需要维护版本的套接字/管道协议，以及一种状态过期的故障模式。文件锁又自带另一种故障模式：持有者崩溃后留下一个过期标记，只能由人来删除。取而代之的做法是：

- **事件流就是队列**：谁注意到文件变化，谁就运行 `ccg update <file>`。
- **数据库本身就是协调基座**（schema v6）：`pending_updates` 表承载变更队列，`update_claim` 单行记录（持有者 + 租约到期时间）就是排他认领。SQLite 的事务原子性取代了所有自定义的锁原语。
- 在认领竞争中落败的一次运行不会等待：它的文件已经入队（入队本身就是一个独立提交的事务），进程随即以退出码 0 退出。持有者会把队列排空直到清空为止，所以工作仍然会被完成——只是晚了几毫秒，发生在赢得竞争的那个进程里。

## 2. 协议

```
ccg update a.cpp b.hpp
```

1. **ENQUEUE（入队）** — 一个短事务把自己（已规范化、已去重）的文件路径插入 `pending_updates`（`INSERT .. DO NOTHING`；表的 `path` 主键会把对同一文件的并发入队折叠为一行）。连接的 SQLite `busy_timeout` 已提前设置就绪（`update-busy-timeout-ms`，默认 600000），因此持有写锁的并发长索引批次会被一直等到结束，而不是失败——并且由于编辑器钩子以分离方式派生更新进程，任何用户可见的东西都不会被阻塞。
2. **CLAIM（认领）** — 一个短的 `BEGIN IMMEDIATE` 事务读取 `update_claim` 行：
   - **没有行、租约已过期、或持有者进程已消失** → 本进程把自己写为持有者，令 `lease_until = now + update-lease-ms`（默认 300000），并进入第 3 步。过期租约可被抢占这一点正是崩溃自愈机制：不会产生过期锁文件。持有者令牌内嵌其 pid，因此当持有者在析构函数来得及运行之前就被杀死（例如宿主杀死一个超时的钩子）时，该认领会被立即接管，而不是让队列一直停到租约耗尽。pid 探测只会在确定无疑时才说"死了"；不含 pid 的令牌退回到纯租约计时。
   - **存在活跃认领** → 立即以退出码 0 退出。工作已被覆盖：持有者的循环会把队列排空直到清空（包括本进程的入队），或者由后续事件使其收敛。
3. **HOLDER LOOP（持有者循环）** — 反复执行：
   1. 一个短的 `BEGIN IMMEDIATE` 事务：刷新租约（心跳）**并** `PEEK`（窥取）整个队列（`SELECT` 所有路径，**不执行 `DELETE`**）。如果心跳匹配不到任何行，说明认领已被抢占（自己的租约在运行中途过期）：停止，队列归抢占者所有。
   2. 记录一个**批次快照**：对数据库/编译数据库所跟踪的每个排队路径，记录该文件当前的内容哈希（缺失/不可读 = 空哈希）。未跟踪的路径不需要哈希。
   3. 在**任何协调事务之外**，经由普通增量引擎（`IndexOptions::seed_files`）处理被窥取的文件：每个种子文件都被强制加入脏集合——种入的主文件会重新解析；种入的头文件属于内容脏，每个 include 闭包到达它的 TU 都会重新解析。引擎自身的批次事务不受影响。
   4. **清除已覆盖项**（一个短的 `BEGIN IMMEDIATE` 事务）：只有当某队列行未被跟踪（既不在数据库中、也不在编译命令中——永远不会有什么去刷新它），或它属于本批次的覆盖集**且**其当前内容哈希仍等于批次快照哈希**且**索引自身记录的 `files.content_hash` 缺失或等于同一个哈希时，才删除该队列行。最后一个条件覆盖"编辑→回退"的残留：字节回到批次前状态会让快照哈希与当前哈希重新一致，而引擎可能已记录了中间状态。索引哈希缺失（文件在批次中途被清除，或从未计算过哈希）不是过期证据——永远保留该行会让持有者循环永不收敛。覆盖集 = 引擎实际重新解析的每个主 TU（包括失败或发现文件缺失的尝试），再加上 include 闭包传播到的每个现存文件。其余一切保持排队。

      这就是不丢失更新规则：在**批次运行期间**落地的编辑会改变哈希（或被 path 主键折叠进同一行），并为下一个批次保留标记——宁可多跑一个批次，也不丢失一次更新。面向用户的语义：把公共头文件 H 编辑两次（第二次发生在第一次编译期间），同时编辑包含 H 的 `C.cpp`；当第二个事件触发的批次结束时（它重新解析了 C），如果 C 的字节没有再次变化，C 的标记即被清除，无需额外编译。
   直到某次窥取返回为空；随后**释放**认领（一个短事务，只删除*自己*的行——`WHERE holder = ?`，因此被抢占的认领绝不会因其过期前任而被删除），并以退出码 0 退出。

   等价不变式：这些批次经由带外部种子的**普通**增量引擎运行，因此静止的数据库与一次普通 `ccg index` 运行对同一树状态得出的结论一致——种子只是增加了确定性（一次保留了 mtime+size 的编辑仍会重新解析，因为事件声明了文件已变化）。

`ccg update --drain`（不带文件）即使没有自己的文件也会认领并循环——它是 Stop 钩子的尾部收敛旗标：会话的最后一批事件在会话结束时被折叠进来。

崩溃行为：

- **认领之前**崩溃不丢失任何东西：入队已提交；下一个事件或 `--drain` 会处理它。
- **持有期间**崩溃：租约过期（在 `update-lease-ms` 之后），下一个更新者抢占认领——自动进行，无需运维介入。此时排队的工作留在 `pending_updates` 里，直到下一个事件或 `--drain`（这是任何无守护进程队列的普通尾部处理）。
- 租约必须超过最坏情况下的单个批次（循环在批次之间心跳，所以只有单个超长批次才能使它过期）。
  这两个配置项都是按数据库配置的：

  | 配置键 | 默认值 | 含义 |
  |---|---|---|
  | `update-lease-ms` | `300000`（5 分钟） | 无心跳时的认领寿命 |
  | `update-busy-timeout-ms` | `600000`（10 分钟） | 协调事务等待并发写锁的时长 |

  用 `ccg config set update-lease-ms 120000` 设置（v6 schema 在引导时创建这两张表）。

每一个 `ccg` 连接——`index`、`msbuild`、`config`、`query`——都在每次打开连接时以第一条语句把默认 30 秒的 `busy_timeout` 设置就绪（SCHEMA.md 第 1 节），因此普通命令会一直等到上述协调事务（每个毫秒级）和短暂的外部锁结束，而不是以 "database is locked" 失败；`update-busy-timeout-ms` 这个配置项存在，是因为更新进程还必须额外等过分钟级的引擎批次。这种不对称此前只指向一个方向：等得更久。

### 时钟源与时钟偏移

租约算术（`lease_until`、心跳刷新、过期检查）使用从机器自身墙钟读取的 unix 纪元毫秒（`GraphStore` 中的 `std::chrono::system_clock`）。每个认领者都是拥有数据库文件的那台机器上的进程，因此该协议不需要任何共享时钟基础设施——但墙钟会跳变（NTP 校正、手动修改），而每个方向都有一个明确且安全的结果：

- **向前跳变**（当前时间突然超前）：一个活跃认领的 `lease_until` 可能被读作已过期，于是下一个更新者提前抢占它。这是安全的方向——引擎运行是幂等的（在同一棵树上重新运行增量引擎会收敛到相同的行），心跳/释放都按持有者字符串匹配，因此原持有者会在下一次窥取时看到 `claim_lost` 并停止，不会触碰抢占者的认领或队列。最坏情况是重复工作，绝不是数据损坏。
- **向后跳变**（当前时间落后）：一个已过期的租约可能被读作仍然活跃，这会推迟抢占，直到时钟追上来（或其后的下一个事件到来）。排队的工作仍会随事件到来而被排空——除了偏移本身之外，不会死锁。

不要把数据库放在由时钟未同步的多台主机写入的共享位置上：跨机偏移会直接叠加到这些窗口上，而且持有者匹配保护不了一个其租约正被外来时钟评判的认领。

## 3. 为编辑器/代理接线钩子（示例）

示例脚本 `scripts/ccg-update-hook.py` 是一个 Claude Code PostToolUse 钩子：它从 stdin 读取钩子 JSON，过滤非语料文件，并**以分离方式**派生 `ccg update`，因此钩子本身在毫秒内返回，而刷新在后台进行。

**本仓库只提供示例——但 CLI 现在会替你接线钩子：**`ccg hook install --project`（或 `--user`）把下面的 PostToolUse / SessionStart / UserPromptSubmit / PreToolUse 条目逐元素合并进
Claude Code 的 `settings.json`（自有条目可识别、卸载干净；CLI.md § *ccg hook*）。手工形态保留给其他编辑器使用，也用于理解写入了什么内容。注意，安装器**不**注册 `Stop` 钩子——下面的配置块是提供给其他客户端的可选手工尾部收敛配置：

`~/.claude/settings.json`（或项目内的 `.claude/settings.json`）：

```json
{
  "hooks": {
    "PostToolUse": [
      {
        "matcher": "Edit|Write|MultiEdit|Update",
        "hooks": [
          {
            "type": "command",
            "command": "python E:/path/to/cpp-code-graph/scripts/ccg-update-hook.py"
          }
        ]
      }
    ],
    "Stop": [
      {
        "hooks": [
          {
            "type": "command",
            "command": "ccg update --drain"
          }
        ]
      }
    ]
  }
}
```

这些钩子如何协作：

- **PostToolUse** 在每次文件编辑工具调用之后触发。脚本按 `tool_name` 和语料扩展名过滤，然后以分离方式派生 `ccg update <file>`。如果刷新已在运行，内建处理器改走快速路径：把文件入队进 `pending_updates` 并记录一条日志（journal）条目，不派生进程、不运行影响查询——钩子从不阻塞编辑器。
- **UserPromptSubmit** 在用户下一次输入之前触发。当没有刷新在运行且队列为空时，它认领批次期间积累的日志条目，对刷新后的数据库重新计算它们的影响面，并注入一条合并的、有界的 `additionalContext`；批次仍在运行时它保持静默（零 stdout）。下一个 PostToolUse 会机会式地使用同一冲刷，PreToolUse 处理器的每一次静默退出也一样（零命中、门控拒绝、截止期限——以及每一次 Read/Glob 调用，它们是纯递送载体）：在无人值守的会话中，代理自己的查询会在它停止编辑后递送最后一个批次。SessionStart 只清扫崩溃/会话残留。
- **Stop**（手工/可选，不由 `ccg hook install` 安装）在代理结束其回合时触发。`ccg update --drain` 认领（或若已被持有则以退出码 0 退出——持有者会排空），并把在上一次 PostToolUse 排空开始之后落地的尾部事件折叠进来。
- **PreToolUse**（matcher 为 `Grep|Bash|PowerShell|Search|Read|Glob`）是第四个只读事件：它监视每一次搜索形态的工具调用——Grep 的 pattern、Bash 或 PowerShell 里的 `rg`/`Select-String` 命令（微秒级的触发词预筛会在任何解析成本发生之前丢弃非搜索命令）、或 Search 工具负载——在搜索运行之前注入目标符号的图谱事实，并且绝不触碰数据库的写路径（3.2 节）。Read 和 Glob 是纯递送载体（不做意图抽取、不做符号查询），处理器的每一次静默退出都会机会式递送摘要积压——在无人值守的会话（无用户提示、无进一步编辑）中，最后一批通过这些查询与读取事件到达模型。把较旧的安装升级到加宽后的 matcher，需要重跑一次 `ccg hook install` 并重启会话（CLI.md § *ccg hook*，升级路径）。

### 3.1 钩子摘要：批次期间落地编辑的结论

当一个批次持有 SQLite 写锁时，一次编辑若不等待写者就无法插入 `pending_updates`。快速路径给这个等待设了上限（150 毫秒），当它竞争失败时，就把 `need_drain = true` 记录进 `<ccg.db dir>/hook-digest/pending-*.json`。一旦认领被释放且 `pending_updates` 为空，冲刷会：

1. 取一个纯消费者锁（`flush.lock`），使并发触发者不会各自输出半份报告。孤儿锁在其 pid 已死、时间戳早于过期窗口、或文件（为空，或因创建与首次写入之间的崩溃而截断）的 mtime 超过该窗口时被回收；在 Windows 上，一个为空但可读的锁证明创建者已经消失，会被立即回收；
2. 把 `need_drain` 路径合并回 `pending_updates`（幂等）并排空；在队列清空之前它保持静默——报告一个仍在追赶的索引会是错误的；
3. 把日志条目重命名为 `claimed-*`（原子认领，恰有一个消费者获胜），重新计算每个文件的影响面，按路径 / 符号 uid / 渲染摘要去重（摘要去重以规范化路径为键，因此不同文件绝不会坍缩成同一条结论），并组装一条上限 1200 字节的消息（截断时以 `等 N 项` 结尾）；
4. 发出，然后删除已认领的文件。认领之后、发出之前发生的崩溃会丢失该轮的结论；被认领的残留文件绝不会被重放，只会按老化策略清除（一小时）。Pending 条目在 24 小时后老化清除；损坏条目被丢弃并在 stderr 上报告。

日志只存储路径与编辑区间——绝不存储编辑时刻捕获的影响数字——因此报告总是反映批次完成时点的数据库。

### 3.2 Grep 时的注入（PreToolUse，I1/V7.1）

第四个被安装的事件 **PreToolUse**（matcher 为 `Grep|Bash|PowerShell|Search|Read|Glob`）在每次搜索形态的工具调用之前触发，工作方向与摘要相反：它不刷新任何东西，它只读取。四条支路汇入同一个共享门控——Grep 的 `pattern` 被直接读取；Bash 的 `command` 在触发词预筛之后经过 tree-sitter 解析的 `rg` 抽取（非搜索命令绝不付出解析成本）；PowerShell 的 `command` 由一个进程内真实引擎解析（`Select-String`/`sls`；只有看起来像搜索的命令才付出引擎加载成本）；Search 的负载字段被直接读取。
每条支路把其负载归约成一条 {patterns, path hint} 查询请求（单个 pattern，或当命令是一个 `rg -e a -e b` / `-Pattern a,b` 的 OR 形态请求时有多个），然后下面的规则统一适用于全部四条支路——任何仍有歧义的东西（多个搜索单元、多个或通配的路径、一个本身不是裸标识符链的 `-F`/`-SimpleMatch` 字面量、动态 `$var` 组成部分）都保持静默：宁可错过一次注入，也不乱猜一次。设计规则：

- **只注入值、感知交替。**每个 pattern 在深度为零的 `|` 处拆分（转义的 `\|` 是字面量；分组内的分支原地不动；为空或超限的形态——多于 8 个分支——丢弃整个 pattern），每个分支必须归约为一个完整的标识符（允许 `A::b` 限定链；`^ $ \b` 锚点、环视守卫以及调用形态的尾部 `\(\)`/`\(` 会被剥除）。C++ 关键字分支作为噪声被丢弃；如果没有分支存活且它们并非全是噪声，该 pattern 可以走下面的受限正则路径。恰有一个存活分支时，行为与经典的单链门控完全一致；多个存活分支作为一次多词项查询运行。如果没有任何东西解析到被索引的符号，钩子不打印任何内容并以退出码 0 退出；搜索绝不会被延迟或拒绝。
- **受限正则路径（默认开启）。**当 `CCG_PRETOOLUSE_REGEX` 允许（`1` 强制开启，`0` 选择退出；未设置或任何其他值退回内建默认值，即开启——该开关只门控这条路径，从不论交替拆分）、且重新拼接的非噪声分支通过护栏（长度 ≤ 64 字节且非纯装饰；PCRE2 引擎编译不了的模式保持静默）时，钩子对符号名表做两层匹配，跳过长于 128 字节的名字。第一层是沿袭已久的全匹配语义（名字须从起点到末尾被整体覆盖，不是搜索）。第一层零命中时，钩子先用空串试探模式一次：能匹配空串的模式对任何名字都成立、不带信息，这次查询就此静默。只有试探不成立、且 `CCG_PRETOOLUSE_REGEX_PARTIAL` 允许时，才重新物化名字表做第二遍扫描，采用部分匹配语义（模式覆盖名字里的一段）。两遍扫描都带截止期探测。引擎跑在解释器档，每次匹配带显式的步数上限：`(a*)*`、`(a|aa)+` 这类量词形态照常放行，匹配触限的名字按不命中处理（未锚定的匹配在每个起点重新计数），它们的数目不为零时每个注入出口都如实披露。唯一一个命中名字走五行/候选列表出口；2-5 个命中名字渲染多词项列表；多于 5 个以分级信封作答——命中总数、能原样重查的名字里字典序最小的前五个、一行收窄建议，同在 1400 字节预算内。
- **选择器语义（2026-10-24）。**剥除后的 pattern 作为选择器跑在符号表上；只有它**唯一**选中的结果才锁定五行格式。多个命中意味着查询本身携带的信息不足以选定一个符号，钩子以**候选列表**作答，而不是乱猜（实地证据：在边际薄弱的歧义上，按出现次数排序挑出的一个答案会主动误导——它得 4/10 而列表得 10/10，且模型信任了注入的身份而非同名行）。列表按引用数列出可调用的同名符号（前 5 个，`(+N more)` 尾巴）及其定义，最后一行教用户如何锁定——用限定名（示例 = 头号候选）或路径过滤器重新 grep。Grep 的 `path` 输入会在唯一性判定之前按定义位置预筛候选，因此一个收窄的 path 能把列表收拢成五行。所有收窄之后仍零命中的保持静默。多词项查询（交替分支、合并的 `-e` pattern、或正则命中的名字）复用这些出口：分支逐个加载候选，按符号 id 去重；当恰有一个分支命中时，答案与该分支的单链查询逐字节一致；当多个分支命中且符号总数至多 5 个时，渲染多词项候选列表（首行披露拼接后的 pattern 与命中数，条目先按分支顺序、再按引用数排序，收尾行教用户对单个词项重新 grep）；总数超过 5 个时，以一行披露计数来代替列表。
- **五行 V7.1 格式，1400 字节预算。**一次命中会渲染身份（限定名 + 参数列表 + 种类 + 父链）、定义坐标、同名消歧（前 3 个同名对手——"那些坐标处的命中属于其他符号"）、带各自最高频调用点的 top-3 调用者（零调用者符号会得到明确的"无调用者的答案"措辞，而不是防御性的猜测），以及派发置信度行。超预算的文本沿规格的降级阶梯处理（用短名、丢弃 "(+N more)" 尾巴、在最后一个 ";" 处截断、带标记硬截断）。候选列表与多词项列表共享同一 1400 字节预算；超预算时从末尾丢弃行（"(+N more)" 计数随之增长），保留头部与提示行；多词项列表还对每个显示字段单独设上限（pattern 64 B、限定名 96 B、路径 64 B，UTF-8 序列安全），并加一道硬截断熔断，使字节上限得到机械保证。
- **只读、进程内、有截止期限守卫。**处理器直接打开数据库（300 毫秒 busy 超时——写者持锁时静默跳过），而不是派生查询子进程，并在每个昂贵阶段之前探测标准钩子截止期限。正则路径把名字表分段物化（每段 20 000 行；段与段之间的一次探测可以放弃余下部分），在此之前还有一次先于任何扫描 SQL 的探测，内存中的扫描循环每 256 个名字再探测一次——每个事件至多两次逻辑全表扫描（第二次只在第一次零命中后发生），绝不多。跨事件不需要去重，因为一次搜索至多映射到一次注入；一次渲染之内，重复的同名/调用者条目按构造即不可能出现（它们以符号为键）。
- **静默退出顺带递送摘要（Opportunistic）。**每一次静默退出——零命中、抽取门控拒绝、截止期限探测、畸形负载、正则开关关闭或其护栏拒绝、能匹配空串的模式被空串试探拦下、第二层开关关闭后第一层零命中、四条搜索支路之外的任何工具、以及每一次 Read/Glob 调用（纯递送载体：不做意图抽取、不做符号查询，递送检查在搜索支路付出任何成本之前运行）——都会尝试一次 `hook_digest_flush(Opportunistic)`，使用与 PostToolUse 顺带递送相同的 900 字节/2.5 秒 PTU 预算。Opportunistic 模式正是安全性的保证：日志目录缺失（一次 stat）、`flush.lock` 被竞争、存在活跃的认领租约、队列未收敛、或积压为空，这些情形都以零成本返回，而排空子进程是仅限 Poll 模式的行为，绝不会在这里发生。任何产出注入消息体的退出——五行块、候选列表、多词项列表、超匹配计数行、或超匹配分级信封——都不顺带递送：1400 字节的注入消息体保持不混杂，积压等待下一次静默退出。成功的递送会留下 `flushed-pretooluse-*` 标记（24 小时老化），其计数以 `digest.preToolUseFlushes` 的形式出现在 `ccg hook status --json` 中；对只读性的唯一放宽是在文件系统上认领/删除日志文件，绝不是数据库的写路径。

### 内建钩子超时：宿主 10 秒上限、9 秒绝对截止期限、分离而非杀死

对大型公共头文件的一次真实编辑完全可能合法地强制一次近乎全量的重解析；没有任何钩子预算能框住它。内建的 `ccg hook posttooluse` 处理器因此绝不让刷新阻塞会话：

- 已安装的 `PostToolUse` 条目带有 `"timeout": 10`——这是宿主的硬上限。
- 处理器朝一个**从进程真实创建时刻起量的绝对截止期限**工作，而不是固定的等待时长。等待 `ccg update` 的时间只剩下：扣除已经流逝的进程年龄、以及留给影响计算与注入写入的 1 秒保留之后的部分（`max(0, budget − elapsed_since_creation − 1000)` 毫秒，实践中约 8 秒）。没有这 1 秒保留，在 12k-TU 数据库上，9 秒等待加上约 1.3 秒的固定后处理会越过宿主的 10 秒上限，注入随之丢失。预算在 Windows 和 Linux 上是 9 秒，在其他 POSIX 平台上是 8 秒——那些平台上进程年龄基线只是一个下界（见下文）。
  - Windows：`GetProcessTimes(GetCurrentProcess())` 的创建时间与 `GetSystemTimeAsFileTime` 相比，因此镜像加载、DLL 初始化和杀毒扫描都落在预算之内。由于这个差值是纯粹的墙钟算术，它会再与一个单调基线（静态初始化的墙钟差，加上 `QueryPerformanceCounter` 与 `GetTickCount64` 两个增量中较大者）交叉校验：因此系统时钟向后跳变时，流逝时间会保持在保守的上界，而不是重置预算。
  - Linux：`/proc/self/stat` 的 `starttime` 与 `/proc/uptime` 相比。
  - 其他 POSIX（包括 macOS）：模块最早的静态初始化只是一个**下界**——发生在它之前的镜像加载不可见，因此测得的进程年龄只会少计。没有无需权限的创建时间 API 可以退回，所以这些平台上的默认总预算降到 8 秒：多出来的这一秒是给不可见镜像加载的实测富余，而不是假设 1 秒保留能吸收它。不要把这个基线当作真实的创建时间；它是尽力而为。
  - 实际等待预算以 `ccg hook: wait budget <n> ms (process age <m> ms)` 的形式打印到 stderr。
- 到截止期限时它**分离而不是杀死**：子进程继续在后台运行直到完成（Windows：`CREATE_BREAKAWAY_FROM_JOB`，使父进程的 job 无法连带终止它，在 job 禁止脱离时退回其他方式；POSIX：`setsid`，使其自成会话）。它的 stdout/stderr 写入关闭时即删除的临时文件，因此父进程先退出时不会泄漏任何东西。
- 随后注入读取
  `[ccg] 已记录 <file>（索引更新在后台继续；影响面基于既有索引）`
  并附上从**既有**索引计算出的符号影响。对纯注释编辑，该影响（以及字段所有者代理）在等待更新**之前**计算，因此即使发生分离，也不必去查询被后台写者持有的数据库。如果截止期限没有给这次预计算留出空间，注入改说 `影响面未查询（索引更新占用，已跳过）`，而不是声称影响无法解析。该文件的排队标记不会丢失：后台批次只会在 §2 的覆盖/哈希规则下清除它。
- `CCG_HOOK_UPDATE_TIMEOUT_MS` 会进一步压缩等待上限（测试套件用一个极小的值来强制走分离分支）；它绝不能延长绝对截止期限。`CCG_HOOK_TOTAL_BUDGET_MS` 与 `CCG_HOOK_POST_RESERVE_MS` 在截止期限测试中覆写 9 秒/1 秒这两个分量；生产环境三个变量都不设置。
- `CCG_PRETOOLUSE_REGEX` 门控 PreToolUse 注入的受限正则路径（§3.2）：`1` 启用，`0` 禁用，未设置或任何其他值都退回内建默认值（当前为启用——闭卷配对评测发现正则路径无害，因此默认随附开启）。该值在每个进程中只读取一次并缓存——钩子在每个工具事件中都是全新进程，因此每个事件至多解析它一次，决策路径上的每次重复检查都是纯内存读取。该开关只门控正则路径：交替拆分与多 pattern 查询永远开启。Windows 注意事项：那里的环境变量查找不区分大小写，因此大小写不同的变体（例如全小写拼法）同样会生效——请只设置一种拼法，不要导出多个大小写变体。
- `CCG_PRETOOLUSE_REGEX_PARTIAL` 门控受限正则路径的第二层（§3.2）：`1` 启用，`0` 禁用（路径在全匹配扫描之后即止，行为与单层时相同），未设置或任何其他值都退回内建默认值（启用）。它的读取与缓存方式与 `CCG_PRETOOLUSE_REGEX` 完全一致；前一个开关关闭时它不起作用。
- 在 POSIX 上，派生子进程中的 `execv` 失败会通过一个 close-on-exec 哨兵管道回报（在管道缺席时，则通过保守的 `exit 127 + 空输出` 检查）。处理器随后走诚实的"无法启动 - 已排队等待下一次排空"分支，而不是声称该编辑已被索引。

| 变量 | 默认值 | 含义 |
|---|---|---|
| `CCG_HOOK_CCG` | `ccg` | 要派生的 ccg 可执行文件 |
| `CCG_DB` | （ccg 默认的 `./.ccg` 文件夹） | 输出文件夹（或其中的某一个配置目录），透传给派生进程 |
| `CCG_HOOK_LOG` | 丢弃 | 把派生进程的 stdout/stderr 追加写入这里 |

注意事项：

- 请在布局文件夹所属的工作目录下运行钩子（或者把 `CCG_DB` 设为 `.ccg` 文件夹 / 其中的某一个配置目录）；`ccg update` 会从派生进程的工作目录解析相对文件路径，而脚本继承了该目录。数据库发现顺序为 `CCG_DB` > `-o`/`./.ccg` 文件夹扫描；恰含一个配置的文件夹会自动选中它，多个配置则需要 `--config`（内建 `ccg hook` 处理器以相同方式解析，且一无所获时保持静默）。
- 该脚本独立可用，无需任何钩子注册即可测试：向它的 stdin 喂一份伪造的 PostToolUse JSON，并把 `CCG_HOOK_CCG` 指向任何能记录自身 argv 的命令——语料过滤、派生参数、毫秒级退出都可以这样观察到（项目的 e2e 门禁覆盖命令语义；脚本自身不带测试钩子，以保持与生产形态一致）。

## 4. `ccg index` 的参与：启动时接管 + 尾部排空

一次完整或增量的 `ccg index` 运行是重量级的权威写者，其解析阶段长达分钟级但只读。因此它通过**在启动时取得认领**并在整个运行期间持续持有，来加入上述同一协议——多写者共存（实地观察到的 `database is locked` 风暴与先删后插外键回滚的共同根源）在设计上即被消解：

1. **解析阶段——持有认领。**打开数据库之后，该运行立即抢占（STEAL）`update_claim`（数据库层的 `steal_update`：与既有的"过期即可抢占"规则相同的 holder/lease_until 写入，只是主动触发），令牌形态与 `ccg update` 相同，即 `ccg-update:pid:<pid>:t<ticks>`——持有者语义不取决于哪个命令持有它，pid 探测因此跨二进制有效。一个活跃持有者被顶替（打印一条 `took over the update lease from '…'` 注记），并在其下一次心跳优雅让位——在批次之间（`peek_pending`）、在其提交事务内（`heartbeat_in_tx`，一个类型化的 `ClaimStolenError` 回滚该批次并停止循环）、或在出队时（`clear_covered`）。当抢占用的 `BEGIN IMMEDIATE` 排在被顶替持有者的在途写锁后面时，索引每次重试打印一行 `waiting to take over the update claim (pid …, queue …)`（1/2/5/10 秒的有界退避，`--wait` 封顶）。`--no-wait` 保持快速失败行为（以退出码 1 退出，而不是接管一个活跃持有者）。索引持有认领期间，钩子只入队——不派生任何更新子进程。
   **解析阶段保活。**解析阶段本身可以超过任何租约（在最大的真实语料上实测 26 分钟，对 300 秒租约），而既有的心跳点（事务内心跳、批次间窥取、批后出队）在解析**完成之前**一个都不触发——一个"已过期但仍活着"的持有者，恰好是钩子的"过期即可抢占"规则会为其派生新写者的对象，索引随后在其第一个提交阶段心跳点发现被抢占并让出整个运行（真实语料验收的 F-1 判定）。因此，一个伴生 jthread 为整个解析窗口续租：它拥有一个**独立的** `GraphStore` 连接（与主线程的连接及语句缓存零共享——不引入新的并发面，与其他所有写者使用同样的短 IMMEDIATE 事务形态），并按 `clamp(lease/4, 1 s, 60 s)` 的节拍执行 `renew_update_lease`。BUSY 会被容忍（下个周期重试；busy 从不意味着被抢占）；一次零行心跳意味着真的被抢占（该线程把自己与主线程停驻——在取写锁之前停止保活——主线程抛出同一个类型化的 `ClaimStolenError`：干净退出，队列归抢占者所有）。提交阶段一开始，事务内心跳随即接管。`ccg update` 的引擎批次免费获得同样的保障（它们把同一个由调用方持有的持有者传入索引器）。测试注入：`CCG_TEST_PARSE_KEEPALIVE=0` 禁用该线程（回归防护的对照分支）；`CCG_TEST_PARSE_HOLD_MS` 拉长解析阶段，`CCG_TEST_TAKEOVER_LEASE_MS` 缩短接管租约，两者结合可在小型夹具上复现该故障场景。
2. **提交前新鲜度复查。**在解析与写事务之间，每个被解析的主 TU 都会重新 stat（`mtime_ns` + size，即指纹自身的同一性字段）。解析期间被编辑的文件就地重新解析（内存中替换——提交阶段存入的是新鲜字节）；消失的文件被降级为一条 `pending_updates` 行（由更新事件流的缺失文件清理接管）。任何明知过期的内容都不会进入提交阶段。
3. **过期快照复查（插入侧兜底）。**解析阶段在所有事务之外对 `file_id` 做快照；在被顶替持有者的在途批次仍在提交的过渡窗口里，快照引用的行可能已经消失。旧 id 流入外键列会以 `FOREIGN KEY constraint failed` 使整个批次中止（在一次受控的双进程实验中 2/2 复现）。因此提交事务会把快照与当前活跃 id 集合做一次 diff（`all_file_ids`）：引用了死 id 的路径会被重新注册（upsert → 新 id，即首次见到该文件的语义），而针对死 id 的快照负载写入（指纹、哈希）则被丢弃。单写者的现实是：零命中，一次常数成本的主键扫描。
4. **事务内心跳。**在提交事务内部，SQLite 不提供嵌套事务，因此短事务心跳模式无法运行——但在**同一个**事务中执行预编译的 `CLAIM_HEARTBEAT` UPDATE 是合法的，索引正是这样做的（跨各存储循环按墙钟节流为每 60 秒一拍）。零受影响行 = 认领已被抢占：运行抛出异常，事务 RAII 把**整个**提交阶段回滚，进程报告 `claim stolen mid-commit - nothing written`。与让两个写者按各自所见的世界状态重放相比，重跑一次过期索引是廉价的。该 UPDATE 匹配 `WHERE holder = ?`，因此被击败的持有者绝碰不到抢占者的行。（`ccg update` 的引擎批次经由调用方持有的持有者使用同一事务内心跳；批次中途被抢占会让持有者循环优雅停止，队列原样保留。）
5. **自适应租约。**认领的租约为 `max(update-lease-ms, 2 × index_commit_ms)`，其中 `index_commit_ms` 是每次 COMMIT 之后记录的实测提交阶段墙钟（首次运行：保守下限取 300 秒默认值的 `2 ×`——租约机制之前的二进制读不到未提交的心跳，只能看到初始的 `lease_until`）。该下限覆盖提交阶段；解析阶段**不**被期望塞进任何租约（在大语料上它是分钟级到几十分钟级）——这正是上面解析阶段保活存在的意义。崩溃由 pid 探测自愈（已死持有者的租约无论 `lease_until` 为何都会被判死）。
6. **释放 + 尾部排空。**COMMIT 之后、认领仍被持有的期间，排队的事件（运行期间钩子入队的编辑）会**在进程内**被收敛：有界的追赶轮次对队列运行普通增量引擎（种子批次、stage-A 快速路径、`clear_covered` 出队），直到队列清空或触及上限（轮数 / 时间预算；配置项 `index-drain-rounds` = 8、`index-drain-budget-ms` = 300000）。输出分三部分且不截断：一条检测注记（`N files changed while indexing - re-processing (drain round K)`）、**完整的**文件列表（每行一个路径，无上限），以及一条收尾结果行（`index drain finished: N round(s), queue empty`，或诚实的残留形态 `index drain stopped after N round(s) - M event(s) still queued`，或被抢占形态）。残留项（预算超限、需要 msbuild 采集联动的项目文件行）交给常规机制处理：一个分离的 `ccg update --drain`（绝不等待、绝不杀死——与钩子使用的同一套平台分离方式）。最后认领被释放（只删自己的行，所有展开路径上都有 RAII；守卫在存储关闭之前被销毁）。

这移除的是：租约机制之前的那套世界——索引的 30 秒 `busy_timeout` 撞上分钟级的更新批次、整个解析工作被回滚（实地观察到 2/2，在 10–60 秒的编辑节奏下机理近乎必然），以及反向的饥饿——一个排队的索引在持有者后面隐形等待，无从得知谁持有什么。它没有移除的是：锁等待本身——接管仍然要排在被顶替持有者的在途批次后面（秒级，stderr 上可见持有者身份）。

`ccg msbuild` 共享同一尾部机制，因此也共享同一批旗标。

## 5. 无钩子的批量/脚本化使用

任何能列出变更文件的东西都可以驱动同一机制：

```
git diff --name-only | while read f; do ccg update "$f"; done
ccg update --drain
```

认领空闲时，每个 `ccg update` 都很廉价；不空闲时，它只是一次队列插入；末尾的排空把队列收敛。

## 6. 项目文件事件：采集-刷新联动

编辑**项目文件**（`.sln` / `.vcxproj` / `.vcxitems` / `.props` / `.targets` / `.filters`）改变的是*语料从哪里来*——TU 列表、include 路径、属性继承——而不是任何 TU 的字节。这类编辑过去被静默丢弃（钩子的语料扩展名过滤从不放行它们，`ccg update <vcxproj>` 只会报 "not tracked"）。联动（msbuild-incr 一期）把它们经由**同一队列**路由进一次重新采集：

1. **钩子门控加宽**：项目文件通过 PostToolUse 过滤器（`cg::util::is_project_file`，ASCII 折叠的后缀匹配），并恰如语料文件一样进入 `pending_updates`。注入行只报告联动事实（项目文件没有符号，因此不运行影响查询）：captured / skipped-unchanged / busy / failed / untracked / still running in the background。
2. **持有者分类**：`ccg update` 持有者窥取队列并拆分每个批次——语料行走普通增量引擎批次，项目文件行进入下面的刷新路径。项目文件行绝不先走"未跟踪"出队分支。
3. **注册表反查（平台中立门控）**：项目根来自数据库的 `project_root` 元数据；注册表是 `<root>/.ccg/msbuild.json`。一行只触发名字等于本数据库配置（`Debug-x64`）的条目，且仅当该行是被注册的解决方案本身、或位于项目根之下。没有根、没有注册表、没有匹配——该行按未跟踪出队（绝不堆积）。非 Windows 机器没有注册表，因此项目事件在那里从不触发采集。
4. **防抖**：派生采集之前，持有者等待队列安静下来（按数据库的元数据 `msbuild_refresh_debounce_ms`，默认 3000；`ccg config set msbuild-refresh-debounce-ms N`），期间租约持续心跳，新的队列行重置窗口（30 秒硬上限）。IDE 的保存风暴坍缩为一次采集。
5. **哈希门（R11，与求值通道成对）**：静默窗之后、锁探测之前，持有者读取刷新快照 `<root>/.ccg/msbuild/<stem>/snapshot.json`（由每次成功求值采集的尾部写回）并现场重推输入身份：快照里每个文件的 sha256（sln、全部成员 `.vcxproj`、全部工程的 import 闭包——闭包是求值腿免费产出）、当前 `INCLUDE` 哈希、下一轮采集的发现缓存会复用的 MSBuild/cl 路径、现场推导的 VCTargetsPath、ccg 版本。全部相等 ⇒ 该事件已被现有语料覆盖：行出队、结论 `skipped-unchanged`、**不派生采集**（IDE 保存多数不改变语料形态的任何输入）。任何不等——无快照、文件变、工具链身份变、坏快照行——落入下面的真实刷新。
6. **互斥**：持有者只**探测** `<root>/.ccg/msbuild/capture-<stem>.lock`（只读 pid 存活探测）；一个活锁会推迟刷新并保留该行。锁本身由 `ccg msbuild` 在其整个窗口期间取得（见 MSBUILD.md）。
7. **交接**：持有者**释放**更新认领，并同步派生 `ccg msbuild <solution> --config C --platform P -o <layout>`（30 分钟上限，分离而不杀死）。采集的索引提交在更新认领上排队（Coordination::wait），因此正是这次交接使整条链无死锁。
8. **成功之后**：持有者重新认领、把项目行出队并**重载**编译命令（新 TU 已被采集自身的增量尾部索引——未变 TU 的指纹使它们保持跳过；被移除的 TU 被清除；引擎本身未被触碰）。如果期间另一个更新拿走了认领，该行跟着它走——最坏情况是一次幂等的重新采集。
9. **失败时保留旧档**：非执行类的 MSBuild 失败（项目 XML 损坏、导入缺失）在不触碰 cdb/db/注册表的情况下中止采集（退出码 1）——联动保留排队行，下一次编辑重试它。数据库绝不会被半刷新。刷新快照属于保留旧档契约的一部分：只在整轮采集成功后写，失败轮绝不会留下一份声称"语料反映这些输入"的快照。

端到端预算：防抖 3 秒（默认）+ 派生采集（默认走求值通道——典型解决方案秒级）+ 增量尾部（6-TU 夹具实测约 0.5 秒；索引一侧只解析真正变更的 TU）。等价事件只付哈希门成本（文件读取加一次目录探测，零子进程）即被 `skipped-unchanged` 吸收。门禁 `ccg_msbuild_e2e` 把整个循环钉住：正常路径、保留旧档、哈希门吸收、修复收敛、根外行、活锁推迟。
并发披露：联动采集进行中另一更新进程对同一项目文件的编辑会让路（busy），被留下的队列行由采集收尾进程自动消费再跑一轮采集（采集幂等，结果正确）——高并发编辑流下采集轮数可能多于事件合并数。
